## Отказоустойчивость

### 1. RTO / RPO по сервисам


| Сервис   | RTO          | RPO                                                   | Обоснование                                                                                                                                                                                                                                                                                                     |
| -------------- | ------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API Gateway    | ~5 мин    | н/д                                                 | Stateless, данных нет. Восстановить быстро, терять нечего.                                                                                                                                                                                                                          |
| Auth           | ~5-15 мин | секунды (креды) / выше (сессии) | Критичен для входа. Данные входа реплицируются (RPO низкий), потеря активных сессий терпима: пользователь перезайдёт.                                                                                                       |
| Account        | ~30 мин   | секунды                                        | Профиль важен, но пара минут недоступности не ломает поток. Реплицируется.                                                                                                                                                                                   |
| Owner          | ~1-2 ч      | секунды                                        | Владельцы менее чувствительны ко времени, чем гости.                                                                                                                                                                                                                           |
| Inventory      | ~1-4 ч      | минуты                                          | Можно деградировать (отдать слегка неактуальное), при потере перезалить из источника.                                                                                                                                                              |
| Inventory Unit | ~30 мин   | секунды                                        | Доступность единиц управляет бронированием, потеря грозит овербукингом, RPO минимальное.                                                                                                                                                         |
| Search         | ~1 ч        | **н/д (rebuildable)**                               | Derived read-model: собственных данных нет, индекс пересобирается из Inventory. При потере — переиндексация, на время восстановления чтение деградирует на БД. |
| Booking        | ~5-15 мин | ≈ 0                                                  | История и состояние броней, рядом с деньгами.                                                                                                                                                                                                                                         |
| Payment        | ~5-15 мин | ≈ 0                                                  | Деньги. Либо всё, либо ничего, потерь быть не должно. RTO не 0, но минимальный.                                                                                                                                                                                    |
| Notification   | ~2-4 ч      | секунды                                        | Долго терпимо: уведомления копятся в Kafka и догонят. RPO низкий за счёт ретенции брокера.                                                                                                                                                               |

### 2. Репликация критичных БД

Критичные по данным: Account, Owner, Inventory, Inventory Unit, Booking, Payment (все PostgreSQL).

**Схема: 1 primary + 1 синхронная реплика + 1 асинхронная**, реплики разнесены по зонам доступности (AZ).

Почему не «2 синхронные»: синхронный коммит в две реплики сразу бьёт по latency записи и по доступности (если хоть одна синхронная реплика недоступна, запись блокируется). Схема 1 sync + 1 async даёт баланс:

- синхронная реплика в другой AZ → RPO ≈ 0 при потере primary
- асинхронная → ещё одна копия и кандидат на чтение, без штрафа на запись
- failover автоматический (Patroni / облачный managed), promotion синхронной реплики в primary

Для Payment и Booking можно включить `synchronous_commit = on` (строгий RPO). Для Inventory/Owner достаточно асинхронной репликации (RPO в секунды терпим, запись быстрее).

### 3. Паттерны отказоустойчивости


| Паттерн      | Где                                                                                                               | Зачем                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Retry**           | синхронные вызовы между сервисами, запись в БД, публикация в Kafka | Сбой часто разовый: сеть моргнула, сервис перезапускался. Вместо ошибки пользователю просто пробуем ещё раз — с паузой между попытками (чтобы не добить то, что лежит) и с ключом идемпотентности (чтобы повтор не создал вторую бронь или второй платёж). |
| **Timeout**         | все сетевые вызовы, особенно внешние (payment/push провайдеры)              | Не висеть на зависшей зависимости. Провайдер не ответил за N секунд → обрываем, уведомление уходит в очередь на повтор (история статусов в БД).                                                                                                                                                                                                     |
| **Circuit breaker** | интеграции с внешними провайдерами (оплата, push/SMS/email)                     | Провайдер сыпет ошибками → размыкаем, не долбим его, отдаём заглушку/откладываем, периодически пробуем half-open. Защищает от каскада и от исчерпания пулов на ожидании.                                                                                                                                                           |
| **Bulkhead**        | изоляция пулов потоков/соединений по зависимостям                        | Отдельные пулы на каждую внешнюю интеграцию и на БД, чтобы залипание одного (например, push-провайдера) не съело все потоки и не утянуло весь сервис.                                                                                                                                                                                             |

### 4. План DR (падение региона)

Исходно: multi-AZ внутри региона + второй регион для DR.

Модель: **active-passive** между регионами.

При падении основного региона:

1. **Трафик** переключается на DR-регион через DNS/global load balancer (health-check не проходит → failover).
2. **БД:** в DR-регионе стоит асинхронная реплика (cross-region). Промоутим её в primary. RPO не нулевой: cross-region async-репликация отстаёт на секунды. Синхронная межрегиональная репликация дала бы RPO ≈ 0, но платой стала бы latency записи на каждом коммите.
3. **Деградация:** на время переключения часть записи недоступна, чтение работает с реплики. Для Payment, если нельзя терять, транзакции в «подвешенном» состоянии дорешиваются после восстановления (сага + идемпотентность это позволяют).
4. **После восстановления** основного региона: досинхронизация (catch-up репликации), затем контролируемый возврат трафика (failback).

Ключевые числа для DR: региональный RTO ~15-30 мин (DNS TTL + промоут БД + прогрев), RPO ~секунды (async cross-region lag).

## Observability

### 5. Ключевые метрики (RED по сервисам + USE по ресурсам + бизнес)

**RED (на каждый ключевой сервис: Gateway, Booking, Search, Payment, Inventory Unit):**

1. Rate — RPS по эндпоинтам/типам операций
2. Errors — доля ошибок, **4xx отдельно от 5xx**, отдельно таймауты
3. Duration — латентность в перцентилях **p50/p95/p99**

**USE (на ресурсы):**

4. CPU utilization %
5. Memory utilization % (+ OOM-события)
6. Disk: место + IOPS
7. Пул соединений к БД — % занятых (приближение к лимиту ловим до отказов)
8. Lag репликации PostgreSQL
9. Глубина/lag очереди Kafka (consumer lag)
10. Saturation: load average, длина очередей, file descriptors

**Бизнес метрики / golden signals:**
11. Успешные бронирования в минуту (по типам)
12. Отменённые/реджекнутые брони в минуту
13. Конверсия: начатые → завершённые брони (просадка = проблема в потоке)
14. Успешные платежи в минуту / доля неуспешных
15. Cache hit rate (Redis) + заполняемость
16. Брони по регионам (аномалии по гео)

### 6. Алерты (пороги + реакция)


| Алерт                                           | Порог                                                          | Реакция                                                                                                                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **5xx error rate**                                   | > 1% запросов за 5 мин (критично > 5%)         | Главный алерт здоровья. Смотрим какой сервис/эндпоинт, свежие деплои, зависимости. Возможен откат релиза.                   |
| **p99 latency**                                      | > 2× baseline за 5 мин                                        | Деградация отклика. p99 — симптом, причину ищем в CDN, кэше, насыщении пула БД, lag репликации.                    |
| **Kafka consumer lag**                               | > 10k сообщений или растёт 10 мин подряд | Упал/затормозил консьюмер. Проверяем инстансы консьюмера, ошибки обработки, не застрял ли на «ядовитом» сообщении. |
| **CPU utilization**                                  | > 80% на инстансе 10 мин                               | Пик или утечка. Смотрим RPS/брони, не упал ли соседний инстанс (нагрузка перетекла), триггерим автоскейл.                         |
| **Пул соединений к БД**              | > 85% занятых                                                | Приближение к отказам. Ищем долгие запросы/локи, проверяем не льёт ли retry-шторм.                                                                    |
| **Репликационный lag**                 | > 10 сек                                                         | Риск для RPO и для чтения с реплик. Проверяем нагрузку на запись и сеть между AZ.                                                                        |
| **Падение успешных платежей** | < 95% от baseline за 10 мин                                  | Бизнес-сигнал. Проверяем payment-провайдера (не разомкнулся ли circuit breaker), сеть, ошибки саги.                                                     |

### 7. Логирование и трейсинг

**Трейсинг (distributed tracing, сквозной trace-id через все хопы):**

- Создание брони: Gateway → Auth → Booking → Inventory Unit → Payment → Notification
- Регистрация: Gateway → Auth → Account
- Поиск: Gateway → Search → Inventory Unit

Нужен, чтобы видеть, на каком сервисе запрос затормозил или упал, и мерить latency по этапам.

**Логирование (структурированные логи с trace-id):**

- Все ошибки (с контекстом и стектрейсом)
- Переходы статусов брони и платежа (аудируемый след: CREATED → ... → PAID)
- Решения circuit breaker (разомкнулся/замкнулся), срабатывания retry
- Что **не** логируем в открытом виде: ПДн и платёжные данные (маскирование), см. безопасность.

## Тестирование

### 8. План нагрузочного тестирования

**Цель:** подтвердить, что система держит пиковую нагрузку из ДЗ 4 (пик чтения ~435 rps, запись с fan-out ~85 writes/s) с приемлемой latency и без ошибок.

**Сценарии:**


| Сценарий                   | Профиль                                | Метрика успеха                                                                                                     |
| ---------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Load (ожидаемый пик)   | ramp-up до пика, держим 30 мин | p99 < целевого SLA, 5xx < 0.5%, нет роста lag                                                                   |
| Stress (поиск предела) | наращиваем до отказа        | найти точку деградации, убедиться что деградирует плавно, а не падает |
| Spike (сезонный x5)        | резкий скачок за секунды | автоскейл успевает, нет каскада ошибок                                                         |
| Soak (выносливость)    | средняя нагрузка 6-12 ч       | нет утечек памяти, нет роста latency во времени, пул соединений стабилен   |

**Отдельно нагрузить критичные пути:** поиск (read-heavy, проверяем кэш и Search), создание брони (write-путь с сагой и локами, проверяем поведение под конкуренцией за одну единицу).

**Инструмент:** k6 / Gatling / JMeter. Тест на staging, приближенном к проду. Метрики успеха снимаем с дашбордов из п.5.

### 9. Chaos-эксперименты

Три эксперимента бьют по **разным** механизмам.

```
Эксперимент №1: Падение инстанса Booking
Steady state:    успешных броней/мин в пределах baseline, 5xx < 0.5%
Гипотеза:        убийство одного пода Booking не уронит поток — трафик уедет
                 на здоровые реплики (HA, >=2 инстанса за балансировщиком)
Blast radius:    1 под из N, staging под нагрузкой
Метод:           kill пода Booking во время load-теста
Наблюдаем:       5xx, p99, rate успешных броней, время до перебалансировки
Rollback:        5xx > 5% либо брони встали — вернуть под
Ожидаемый вывод: достаточно ли реплик и верно ли настроены health-check/LB
```

```
Эксперимент №2: Деградация внешнего payment-провайдера
Steady state:    доля успешных платежей, latency payment-пути
Гипотеза:        при ошибках/таймаутах провайдера сработает circuit breaker,
                 поток не закаскадит, брони уйдут в PENDING_PAYMENT, а не в 5xx
Blast radius:    только интеграция с payment-провайдером, staging
Метод:           инжект задержки +5с и 50% ошибок на вызовах провайдера
Наблюдаем:       состояние circuit breaker, таймауты, насыщение пула платежей,
                 корректность статусов саги
Rollback:        зависания распространились на другие сервисы (bulkhead не держит)
Ожидаемый вывод: верны ли пороги circuit breaker и изоляция пулов (bulkhead)
```

```
Эксперимент №3: Потеря зоны доступности (AZ)
Steady state:    система в SLA по чтению и записи
Гипотеза:        потеря одной AZ выдерживается в пределах RTO/RPO — синхронная
                 реплика в другой AZ промоутится, трафик перераспределится
Blast radius:    одна AZ из трёх, staging
Метод:           отключить сетевой доступ к инстансам и БД-реплике в одной AZ
Наблюдаем:       время failover БД, RPO по факту (потерянные записи), 5xx в момент
                 переключения, восстановление записи
Rollback:        запись не восстановилась за целевой RTO
Ожидаемый вывод: реальны ли заявленные RTO/RPO, корректен ли автоматический failover
```

## Безопасность (кратко)

### 10. Аутентификация / авторизация

- **Аутентификация:** OAuth 2.0 / OIDC, JWT как access-token (короткоживущий, 15 мин) + refresh-token (долгоживущий, хранится безопасно). Валидация токена на Gateway.
- **Авторизация:** RBAC — роли `guest`, `owner`, `admin`. Проверка прав на ресурс (гость видит только свои брони, владелец только свои объекты).
- **Доп. меры:** rate limiting на Gateway (анти-брутфорс, анти-DDoS), отдельная защита админки.

### 11. Шифрование и секреты

- **В транзите:** TLS на всех внешних и межсервисных соединениях.
- **В покое (at rest):** шифрование БД и бэкапов (ПДн: ФИО, дата рождения, email, phone, паспортные данные).
- **Платёжные данные:** не храним у себя карты, делегируем провайдеру (токенизация), это снимает основную часть PCI-DSS.
- **Секреты:** не в коде и не в переменных окружения в открытом виде, а в Vault / облачном Secrets Manager (KMS), с ротацией.
- **Логи:** маскирование ПДн и платёжных данных.
