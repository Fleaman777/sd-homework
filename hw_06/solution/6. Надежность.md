# 6. Надёжность

## 6.1. RTO/RPO по сервисам

**RTO** (Recovery Time Objective) — за сколько сервис должен восстановиться после отказа (допустимый простой).
**RPO** (Recovery Point Objective) — за какой период допустима потеря данных при аварии.

Сервисы сгруппированы по критичности: цифры назначены не одинаково, а по важности (жёсткий RTO/RPO дороже — требует синхронной репликации и горячего резерва).

| Сервис | Критичность | RTO | RPO | Обоснование |
|---|---|---|---|---|
| Auth | Критичный | 2 мин | ~0 | Без него приложение недоступно. Синхронная репликация даёт RPO ~0. Потеря сессий не страшна (перелогин) |
| Account | Критичный | 1 мин | ~0 | Потеря данных пользователя недопустима. Синхронная репликация → RPO ~0 |
| Telemetry Ingest | Важный | 20 мин | ~0 | RPO обеспечивает не реплика БД, а буфер Kafka: непрочитанное переживает падение потребителя. Consumer дочитывает с offset |
| Telemetry Query | Важный | 30 мин | н/п | Stateless-чтение с реплик, своих данных не хранит — терять нечего. Важен только RTO |
| Diagnostic | Важный | 20 мин | 10 мин | Потеря сервиса → нет заключения; fallback на сырые коды. История заключений/чатов терпит потерю за минуты, асинхронной репликации достаточно |
| Content | Важный | 30 мин | 15 мин | Без фото смысл можно передать текстом → мягче. RPO относится к метаданным (PostgreSQL); файлы в S3 надёжны на стороне провайдера |
| Notification | Важный | 15 мин | ~0 | Алерты рождаются в Kafka и там лежат; consumer дочитывает с offset. Задержка доставки терпима, потери нет |
| Support | Некритичный | 1 час | 25 мин | Тикет можно отправить позже. Одна реплика достаточна |

**Принцип:** буферизация через Kafka улучшает RPO асинхронных сервисов (Ingest, Notification) — события переживают падение потребителя, потому что непрочитанное хранится в брокере. Их RPO определяет сохранность Kafka (RF3), а не собственная БД.

## 6.2. Схема репликации

| Хранилище | Схема | Тип | Обоснование |
|---|---|---|---|
| Auth (PostgreSQL) | master + 1 реплика | Синхронная | Критичность доступа, RPO ~0 |
| Account (PostgreSQL) | master + 2 реплики | Синхронная | Данные пользователей терять нельзя, RPO ~0 |
| TS DB | master + 3 реплики | Асинхронная | Реплики для read-масштабирования (ADR-002) и отказоустойчивости; лаг для телеметрии допустим |
| Diagnostic (PostgreSQL) | master + 1 реплика | Асинхронная | История терпит небольшую потерю |
| Content (PostgreSQL) | master + 1 реплика | Асинхронная | Метаданные медиа; файлы — в S3 (надёжность провайдера) |
| Kafka | 3 ноды, RF3 | Кворум | Сохранность буфера и событий |
| Redis | 2 ноды | — | Кэш, не источник правды; при потере перестраивается (cache-aside) |
| Support (PostgreSQL) | master + 1 реплика | Асинхронная | Некритичный |

**Связь с RPO:** тип репликации определяет RPO. Синхронная (Auth, Account) → RPO ~0, но запись чуть медленнее. Асинхронная (телеметрия, диагностика) → RPO = лаг репликации, что допустимо для этих данных.

## 6.3. План DR (Disaster Recovery)

**Мультизонность (multi-AZ).** Все критичные компоненты размещены в нескольких зонах доступности, чтобы падение одной зоны не убивало систему. Заложено в сайзинге (запас ×2 на отказ).

**Бэкапы.** Реплика защищает от падения ноды, бэкап — от катастрофы (потеря всех зон) или порчи данных (ошибочная миграция, удаление). Поэтому частота бэкапа определяет RPO только в сценарии полной аварии, в обычном падении спасает реплика.

| Сервис | Частота бэкапа | Защищает от |
|---|---|---|
| Auth | 1 раз/сутки | Порча/потеря данных пользователей Auth (сессии восстановимы перелогином) |
| Account | 1 раз/час | Двойная авария зон или порча данных аккаунтов |
| Telemetry Ingest / TS DB | 1 раз/12 ч | Порча БД; при пропуске данные добираются из Kafka по offset |
| Diagnostic | 1 раз/12 ч | Историю заключений терять терпимо |
| Content | 1 раз/12 ч | Метаданные (PostgreSQL); файлы в S3 не бэкапятся вручную |
| Notification / Query / Support | — / по расписанию | Query и Notification своих критичных данных не хранят |

**Процедуры восстановления — два класса:**

1. **Stateful-хранилища** (Auth, Account, Diagnostic, Content): падение ноды → переключение на реплику; катастрофа/порча → восстановление из бэкапа.
2. **Консьюмеры Kafka** (Telemetry Ingest, Notification): восстановление дочитыванием с последнего offset. Буфер гарантирует, что непрочитанное не потеряно. Единая логика для обоих: понять, с какого момента остановились, и добрать.

**Graceful degradation по сервисам:**
- **Telemetry Ingest:** под перегрузкой временно отключается алертинг (сохраняется главное — запись данных); при отставании TS DB данные копятся в Kafka (буфер), запись идёт медленнее, но без потерь; в крайнем случае — приём только критичных метрик.
- **Telemetry Query:** в пик отдаются прореженные данные (downsampling), урезается глубина истории, отключаются тяжёлые агрегаты.
- **Diagnostic:** при недоступности LLM — fallback на выдачу сырого кода ошибки. Потеря Redis не требует восстановления: кэш прогревается заново через cache-aside (первые запросы дороже/медленнее).
- **Content:** при недоступности медиа запрос к LLM всё равно уходит с текстовым описанием.

**Fallback внешних интеграций:**
- LLM недоступен → сырые коды.
- Push-провайдер недоступен → email как резервный канал.
