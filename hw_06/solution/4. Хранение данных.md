# 4. Хранение данных

## 4.1. Выбор БД с обоснованием

Система использует polyglot-хранение: каждый тип данных ложится в хранилище под свой профиль нагрузки.

| Данные | Хранилище | Обоснование |
|---|---|---|
| Телеметрия (поток) | **TS DB** (ClickHouse или аналог) | Высокочастотная запись (до 200k точек/сек), временные ряды, колоночное сжатие в разы, партиционирование по времени, чтение с реплик. Реляционка такой поток не держит. |
| Аккаунты, устройства, машины, коды, тикеты | **PostgreSQL** | Классические реляционные данные с связями и транзакциями, объём небольшой, шардирование не нужно — хватает одной ноды с репликами. |
| База знаний RAG | **pgvector** (PostgreSQL + векторное расширение) | Семантический поиск по эмбеддингам для диагностики. Векторный индекс поверх привычного PostgreSQL, не нужен отдельный векторный движок. |
| Медиа (фото) | **S3** (объектное хранилище) | Бинарные файлы, дёшево, масштабируется независимо; метаданные — в PostgreSQL, сами файлы — по ключу в S3. |
| Кэш ответов диагностики и справочника кодов | **Redis** | Быстрый доступ, снижает дорогие вызовы LLM и обращения к PostgreSQL; общий на все инстансы. |
| Буфер телеметрии, шина событий | **Kafka** | Буфер перед записью (сглаживает пики), лог с перечитыванием при сбоях, несколько консьюмер-групп поверх одного потока. |

**Принцип связей:** у каждого сервиса своя БД. Связи между сервисами — по id, без физических внешних ключей в чужие базы.
**Правило именования:** первичный ключ таблицы — `id` (тип UUID); ссылка на другую сущность — `<entity>Id` (тип UUID).

## 4.2. Схемы данных

### Auth (PostgreSQL)

Stateless-аутентификация на JWT: access-токен не хранится (валидируется по подписи локально на гейтвеях), в базе только refresh.

```
auth_session: id, userId, refreshToken, createdAt, updatedAt, deactivatedAt
```

Отзыв: короткий TTL access-токена (~15 мин), при необходимости — деактивация refresh в базе.

### Account (PostgreSQL)

Разнесено на 4 сущности: профиль, сканер (OBD2-донгл), машина, телефон пользователя.

```
account: id, status (NEW, VERIFIED, DECLINED, DELETED), email, firstName, secondName, createdAt, updatedAt

scanner (OBD2-донгл): id, serialNumber, accountId, carId, status (ACTIVE, BLOCKED, UNLINKED), createdAt

car: id, accountId, brand, model, year, vin, createdAt

device (телефон пользователя): id, accountId, pushToken, os, appVersion, createdAt
```

Привязка сканера к машине — текущая (`carId` в scanner). История переездов — backlog.

### Diagnostic (PostgreSQL + pgvector)

```
diagnostic: id, accountId, carId, conclusion (jsonb), contentId, carCodes (varchar[]), chatId, createdAt

chat: id, accountId, createdAt

message: id, chatId, sender (USER, LLM), text, createdAt

code_info (справочник эталонных кодов, ведёт Support):
  id, code, description, applicableBrands (массив, пусто = универсальный OBD2),
  manufacturerSpecific (bool), createdAt, deactivatedAt

rag (pgvector): id, chunk (текст), embedding (вектор), metadata (jsonb: source, brand/model, тип), createdAt
```

Машина не дублируется: diagnostic ссылается на car по `carId`. Конкретная машина в справочник кодов не пишется — берётся из car.

### Content (PostgreSQL + S3)

```
meta: id, accountId, diagnosticId, mimeType, s3key, size, ttl, createdAt
```

Файлы в S3 по ключу `s3key` (полный URL собирается в рантайме). `ttl` заложен на будущее (автоочистка), на MVP не применяется.

### Support (PostgreSQL)

```
support: id, email, firstName, secondName, roles[] (на MVP одна роль, задел под RBAC),
         status, createdAt, updatedAt, deactivatedAt

support_ticket: id, accountId, assignedTo (support.id, может быть пустым),
                subject, status (NEW, IN_PROGRESS, WAITING, RESOLVED, CLOSED), createdAt, updatedAt

support_message: id, ticketId, sender (USER, SUPPORT), text, createdAt
```

Обращения поддержки отделены от чата с LLM (разный жизненный цикл).

### Telemetry (TSDB)

```
telemetry: scannerId, metricId, accountId, timestamp, value (double)
```

- Ключ композитный (`scannerId + metricId + timestamp`), отдельного id на точку нет.
- `accountId` денормализован, проставляется на момент записи по текущей привязке сканера, не переписывается (история владельцев не путается при перепривязке).
- Партиционирование по времени (например, по суткам). Retention переносит партиции старше горячего окна (7 дней) в cold-архив.
- `metric` (справочник параметров) — в конфиге сервиса, не в потоке (список статичный).

### Notification (PostgreSQL)

```
notification: id, type (PUSH, EMAIL), userId, source, content, subject,
              status (NEW, IN_PROGRESS, SENT, RETRY, FAILED), retryCount, createdAt
```

Адрес/токен доставки не хранится — подтягивается из Account по `userId` (device.pushToken для push, account.email для email) в момент отправки.

## 4.3. Схема шардирования

Шардирование применяется точечно — только к телеметрии. Это единственный контур, растущий под нагрузкой и по объёму (10 000 RPS в пик, десятки ТБ в год). Остальные БД (Account, Auth, Support, Diagnostic, Content, Notification) небольшие, живут на одиночных нодах с репликами.

**Ключ шардирования:** `scannerId`. Всё устройство целиком ложится на один шард, поэтому история поездок конкретного сканера локальна (читается с одной ноды), а перепривязка сканера к другому аккаунту не разрывает его данные между шардами. `accountId` в ключ не входит (он денормализован в точках для фильтрации, но не для распределения).

**Стратегия:** consistent hashing с виртуальными нодами. Обычный hash по модулю числа нод при доливе шарда потребовал бы перераспределить почти все данные (меняется N). Consistent hashing перемещает только часть данных при добавлении ноды, что критично для растущего парка устройств. Виртуальные ноды дают более ровное распределение.

**Соотношение с партиционированием:** две независимые оси. Шардирование по `scannerId` определяет, на какой ноде лежат данные. Партиционирование по времени внутри каждого шарда определяет временной кусок (для hot/cold и retention). Они складываются, не конфликтуют.

**Отсутствие горячих шардов:** каждый сканер шлёт однородный поток (1 батч/сек), нагрузка по устройствам равномерна, перекос (hot partition) из-за отдельного устройства не возникает.

## 4.4. Стратегия кэширования

**Основной кэш — ответы диагностики.** Диагностика редкая по частоте, но дорогая по стоимости (вызов внешнего LLM). Кэш бьёт по этой дорогой операции.

**Паттерн cache-aside:** запрос приходит с кодами ошибок → из `код + бренд + модель + год` собирается ключ → проверяется Redis. При попадании возвращается готовый ответ. При промахе идёт полный цикл (справочник кодов, RAG, Content, LLM), результат перед возвратом кладётся в кэш.

Ключ переиспользуем между пользователями: у разных владельцев одной модели с одной ошибкой ответ общий, один расчёт LLM обслуживает многих.

**Кэш общий (Redis), не локальный.** У Diagnostic несколько инстансов, локальный кэш давал бы дублирование и низкий hit-rate; общий Redis держит единый пул.

**Вытеснение и свежесть — три механизма вместе:**
- **LRU-eviction** (Redis maxmemory + политика) — холодные ключи вытесняются автоматически, кэш не раздувается.
- **TTL** как страховка свежести — ответ живёт ограниченное время и перегенерируется с учётом обновлённых знаний.
- **Явная инвалидация при правках Support** — обновил расшифровку кода или пополнил RAG, связанные ключи сбрасываются сразу. Дёшево в реализации, даёт консистентность там, где новое знание важно подхватить немедленно.

**Дополнительный кэш — справочник кодов (`code_info`).** Горячий статичный справочник, читается на каждой диагностике, меняется редко — держится в Redis, чтобы не ходить в PostgreSQL каждый раз.

**Не кэшируется — телеметрия.** Живой поток постоянно меняется, кэш поверх бессмыслен. Масштабирование чтения обеспечивают реплики TS DB.

**Эффективность:** hit-rate зависит от плотности одинаковых моделей в базе пользователей. Даже частичное попадание оправдано — экономит дорогой вызов LLM.
