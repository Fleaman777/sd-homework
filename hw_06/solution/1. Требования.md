# 1. Требования

## 1.1. Акторы

### Люди
- **Автовладелец** — диагностирует свою машину, работает через мобильное приложение и веб.
- **Администратор** — управление пользователями и устройствами, ответы на обращения, ведение базы знаний RAG и справочника кодов ошибок, наблюдение за мониторингом. На MVP роль одна, разграничение прав (RBAC) — в backlog.

### Внешние системы
- **OBD2-сканер** — источник телеметрии. Связь по BLE только с мобильным приложением, в облако напрямую не ходит.
- **LLM-провайдер** — внешний мультимодальный инференс для диагностики и чата. Вызов по REST.
- **Провайдеры уведомлений** (APNs / FCM / email) — доставка push и email.

## 1.2. Функциональные требования

### Автовладелец
Доступно с мобильного приложения и веба, кроме захвата телеметрии (только мобильное приложение по BLE).

- Регистрация и авторизация.
- Привязка OBD2-сканера к аккаунту.
- Просмотр показателей машины в реальном времени.
- Просмотр истории поездок и диагностических заключений.
- Получение ИИ-заключения о состоянии машины.
- Диалог с ИИ-ассистентом.
- Получение алертов при критических показателях.
- Загрузка медиаконтента (фото) для уточнения проблемы.

### Администратор
- Управление пользователями и устройствами.
- Ответы на обращения пользователей.
- Ведение базы знаний RAG.
- Ведение справочника кодов ошибок.
- Наблюдение за мониторингом системы.

## 1.3. Нефункциональные требования

Профиль нагрузки асимметричный: тяжёлый поток в приёме телеметрии (ingestion), редкие запросы в диагностике.

| Параметр | Значение |
|---|---|
| MAU | 200 000 |
| DAU | ~60 000 (30% от MAU) |
| Пик одновременных донглов | ~10 000 (вечерний час пик) |
| Частота отправки с донгла | 1 батч/сек |
| Параметров в батче | 15–20 |
| RPS ingestion (пик) | ~10 000 |
| RPS ingestion (среднее) | ~2 500 |
| Peak Factor | 4 |
| Точек данных в секунду (пик) | ~150 000–200 000 |
| RPS на чтение (дашборды, история) | сотни |
| Частота диагностики | ~1 раз/месяц на пользователя |

## 1.4. Ограничения

- Хорошие LLM-модели дороги, бюджет на инференс конечен.
- Сканер обязателен: без него продукт не имеет смысла.
- ИИ в ядре продукта: без него это не та система, что проектируется.
- BLE в браузере ненадёжен: на телефоне полноценно работает только мобильное приложение.
- OBD2 читает ограниченный набор параметров, состав зависит от марки и протокола; более дорогой адаптер видит больше.
- Ограниченный радиус BLE: при захвате нужно быть рядом с машиной.
- iOS ограничивает фоновую активность: непрерывный захват при погашенном экране не гарантирован, нужен буфер и досылка данных.

## 1.5. Риски и меры смягчения

| Риск | Смягчение |
|---|---|
| LLM недоступна, диагностика встаёт | Fallback на выдачу сырого кода ошибки, чтобы пользователь мог обратиться к мастеру |
| LLM неверно трактует код, ложное «всё ок» (юридический, репутационный, финансовый риск) | Дисклеймер о возможной некорректности, показ исходного кода, рекомендация проверки у специалиста |
| Не выдержали нагрузку в пик, телеметрия недоступна | Graceful degradation: приоритет приёму данных и LLM, временное упрощение живого дашборда |
| Утечка персональных данных (геолокация, стиль езды) | Шифрование, минимизация собираемых данных, регулярное обновление софта |
| Отказ push-провайдеров, пропуск важного алерта | Резервный канал (email), повторная доставка |
| Испорченные данные со сканера (нестабильная связь, глюки) | Валидация на входе, отбраковка выбросов, устойчивость к разрывам и досылке |

## 1.6. Backlog (не входит в scope MVP)

- Оценка деградации и износа авто (тренды и аналитика по накопленной телеметрии). Просмотр истории поездок и заключений входит в MVP, аналитика деградации — нет.
- Разграничение прав (RBAC): выделение оператора поддержки из администратора.
- Видео и аудио в диагностике (на MVP только фото).
