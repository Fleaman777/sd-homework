## Исходные параметры

- 3 млн MAU, 300K DAU
- 1 бронирование на пользователя в месяц
- Пик: x5 в сезон отпусков

---

## 1. Расчёт RPS

**Чтение.**
Беру 25 запросов на чтение за один заход пользователя. Для booking-браузинга это реалистично: поиск, листание выдачи, открытие нескольких карточек за сессию.
```
25 × 300K = 7 500 000 чтений/день
7 500 000 / 86400 ≈ 87 rps (среднее)
пик: 87 × 5 ≈ 435 rps
```

**Запись.**
Одно бронирование это не одна запись. Сага раскладывается на создание Booking, переходы статусов, запись Inventory Unit, Payment с его статусами, outbox и события. Реально 10-20 операций записи на одно бронирование.
```
3 млн бронирований/мес / 2 592 000 сек ≈ 1.16 бронирований/с
с fan-out ~15 операций: ≈ 17 writes/s (среднее)
пик: × 5 ≈ 85 writes/s
```
Запись владельцев (добавление объектов) незначительна и размазана по времени.

**Соотношение чтение/запись ≈ 25:1** на уровне бизнес-операций (87 rps чтения против ~1 бронирования/с на входе). Система выражено read-heavy, это обосновывает реплики на чтение, CQRS и кэш.

## 2. Расчёт хранилища

### Реляционные данные (одно бронирование)

Размер строк на одно бронирование:
```
Booking:        id(16) + inventoryUnitId(16) + guestId(16)
                + status(4) + additionalInfo jsonb(~32) + createdAt(8) ≈ 90 байт
Payment:        ≈ 100 байт
Inventory Unit: ≈ 100 байт
--------------------------------------------------------
Итого на бронирование ≈ 300 байт (три записи вместе)
```

Пересчёт объёма:
```
1.16 бронирований/с × 300 байт ≈ 350 байт/с
× 86400 ≈ 30 МБ/день
× 365 ≈ 11 ГБ/год (чистые данные)
× 3 года ≈ 33 ГБ
```

С учётом эксплуатации:
```
+ индексы (×~2.5)        → ~28 ГБ/год на узел
× 3 реплики              → ~85 ГБ/год, ~250 ГБ за 3 года
```
Плюс WAL, но на фоне десятков гигабайт это копейки.

**Вывод:** реляционные данные крошечные. Основной объём в медиа.

### Медиа (фото объектов)

```
1 млн объектов
50 фото в среднем на объект (квартира ~20, отель с номерами ~100)
2 МБ на фото (оригинал)
--------------------------------------------------------
50 × 2 МБ × 1 000 000 = 100 ТБ (оригиналы)
+ превью и ресайзы под разные экраны (×~1.3-1.5) → ~130-150 ТБ
+ метаданные ~1 ГБ
```
Каталог растёт за 3 года, объём будет выше стартовых 100 ТБ. S3 реплицирует сам, отдельно множить не надо.

### Итог по хранилищу

| Данные | Хранилище | 1 год | 3 года |
|---|---|---|---|
| Реляционные (с индексами и репликами) | PostgreSQL | ~85 ГБ | ~250 ГБ |
| Медиа | S3 | ~130 ТБ | растёт с каталогом |

## 3. Расчёт bandwidth

Трафик делю на API (JSON, мелкий) и медиа (почти весь). Вес отдаваемого фото не равен весу хранимого: храню оригинал 2 МБ, отдаю ресайз.

**Считаю от сессий, а не от общего RPS:**
```
сессий/с в пик ≈ 300K / 86400 × 5 ≈ 17

на одну сессию отдаётся:
  превью выдачи:   40 шт × 150 КБ ≈ 6 МБ
  детальные фото:  3 карточки × 15 фото × 400 КБ ≈ 18 МБ
  ------------------------------------------------
  ≈ 24 МБ на сессию

пик к пользователям: 17 × 24 МБ ≈ 400 МБ/с
API (JSON):          435 rps × ~15 КБ ≈ 6.5 МБ/с
```

| Поток | Пик |
|---|---|
| К пользователям (всего) | ~400 МБ/с |
| На origin (S3/сервисы), CDN снимает ~90-95% | ~20-40 МБ/с |

## 4. Оценка ресурсов

**Инстансы.** Один инстанс 4 vCPU держит ~1000 rps, по нагрузке (пик чтения 435 rps) хватило бы 2-3. Реальное число инстансов диктует HA и реплики, а не RPS.
```
~10 сервисов × 2 реплики = 20
+ критичные (Account, Payment) по 3 = +2
≈ 26 инстансов на 4 vCPU
```

**Базы данных.** Один кластер PostgreSQL с репликами, размазанными по зонам доступности (AZ). Стартовый размер ~150 ГБ с запасом, автоскейл при заполнении на 2/3. S3 реплицируется из коробки.

## 5. Расчёт стоимости (в месяц)

```
Сессий в месяц ≈ 300K × 30 ≈ 9 млн
Egress к пользователям ≈ 9 млн × 24 МБ ≈ 216 ТБ/мес
```

| Статья | Расчёт | Стоимость/мес |
|---|---|---|
| Egress (с CDN, ~$0.02/ГБ эффективно) | 216 000 ГБ × $0.02 | ~$4 500 |
| S3 (100 ТБ hot) | 100 × $23 | ~$2 300 |
| Compute | 26 × $120 | ~$3 100 |
| Managed PostgreSQL | | ~$100 |
| **Итого** | | **~$10 000** |

Для сравнения egress без CDN: 216 000 ГБ × $0.085 ≈ $18K, то есть CDN экономит ~$13K/мес на одном egress.

**Вывод:** самая дорогая статья это egress (раздача медиа), затем хранилище, и только потом compute. Compute самая мелкая из трёх крупных статей, вопреки первому впечатлению.

## 6. Оптимизация

Порядок по реальному влиянию на счёт:

1. **CDN.** Бьёт по самой большой статье (egress). При кэш-хите egress с origin падает в разы.
2. **Оптимизация изображений.** WebP/AVIF вместо JPEG, адаптивные размеры под экран, lazy-load. Уменьшает затраты на egress.
3. **Тиринг хранилища.** S3 Intelligent-Tiering на 100 ТБ: фото архивных и непопулярных объектов уходят в холодные классы автоматически, дешевле hot.
4. **Reserved / Spot для compute.** Скидка до ~40% при резервировании на 3 года.
5. **Кэш (Redis) на горячие выдачи и карточки.** Снимает нагрузку с БД и compute, повышает кэш-хит на медиа через CDN.

**Главный вывод.** Нагрузка на запись мелкая, читающий трафик это в основном картинки, поэтому CDN и оптимизация изображений решают одновременно и bandwidth, и стоимость. Реляционная часть системы по объёму и деньгам незначительная.
